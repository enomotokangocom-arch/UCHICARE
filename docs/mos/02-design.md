# Uchi Management OS — 設計書（Phase 1〜3）

最終更新: 2026-10-16 / 対象: Phase 1（データ統合）・Phase 2（損益計算）・Phase 3（経営ダッシュボード）

データの実構造は [`01-data-spec.md`](./01-data-spec.md) を参照。AI改善提案などの追加機能は Phase 1〜3 完了まで着手しない。

## 1. 全体方針

| 方針 | 実装での担保 |
|---|---|
| 列名・値を推測しない | すべての取込ファイルを実ファイルで確認し、見出しラベルで形式を検証してから読む。検算（合計＝内訳の和、合計行との一致など）に通らない行・シートは取込まない。ファイルに無い情報（ZEST の対象年月）は利用者が指定し、日数で検算する。 |
| 推測値を実績として保存しない | 取込テーブル（実績）には **ファイルに書かれていた値だけ** を保存。推計は再計算結果（`MonthlySnapshot`）にのみ存在し、必ず `ESTIMATED` 状態が付く。空欄を 0 で補完しない。試算表の未経過月（全科目0）は保存しない。 |
| サンプルと実データの区別 | すべての取込データに `origin = REAL / SAMPLE`。画面アップロードは常に `REAL`、サンプルは `npm run mos:seed-sample` のみが作る。集計は origin を混ぜない。サンプル表示中は全画面に警告帯を表示。 |
| 確定月を無断で書き換えない | `MonthClose` が `CLOSED` の月に関する新しい値は `HELD`（保留）として保存し、計算には使わない。確定解除は管理者のみ・理由必須・監査ログ記録。確定月のスナップショットは再計算しない。 |
| 個人情報の非表示 | 利用者の氏名・住所・年齢・公費番号などの医療情報は **DBに保存しない**（取込処理がその列を読まない。利用者ID・職員名は HMAC でハッシュ化）。銀行明細の摘要（個人名を含みうる）は管理者・事務のみ閲覧。職員ロールは集計値のみ。 |
| 非公式な自動ログインをしない | iBow・ZEST・銀行への自動ログイン／スクレイピングは実装しない。取込はユーザーが公式画面からダウンロードしたファイルのアップロードのみ。 |
| 毎朝8時の自動再計算 | 再計算は冪等なサービス関数。`/api/mos/cron/recalculate`（`CRON_SECRET` 認証）を JST 8:00（UTC 23:00）に呼ぶ。`vercel.json` に cron 定義、他環境は `npm run mos:recalc` を crontab 等で実行。 |

## 2. データベース設計（PostgreSQL / Prisma）

スキーマ本体: [`prisma/schema.prisma`](../../prisma/schema.prisma)

### 2.1 ER 概要

```
User ─┬─< ImportBatch ─┬─< ImportIssue
      │                ├─< BankTransaction >── BankAccount
      │                ├─< RevenueFact          （居宅売上管理表 / iBow売上）
      │                ├─< TrialBalanceLine     （試算表）
      │                ├─< VisitRecord          （ZEST予定 / iBow実績）
      │                └─< MetricValue          （ZEST経営指標）
      ├─< AuditLog
      └─< MonthClose
ClassificationRule（銀行明細の自動分類）
AccountTitle（勘定科目マスタ：区分・固定/変動/人件費・直接/共通/本部）
Target（月次目標） StaffCapacity（職種別稼働可能時間） AppSetting（配賦基準・照合許容差など）
RecalcRun ─< MonthlySnapshot（月×部門の損益・KPI計算結果）
```

### 2.2 主要テーブル

| テーブル | 役割 | 主なカラム / 制約 |
|---|---|---|
| `User` | 利用者 | `role: ADMIN（経営者）/ MANAGER（事務・管理者）/ STAFF（職員）`、`passwordHash`(bcrypt) |
| `ImportBatch` | 取込1回＝1行（取込履歴） | `sourceType`, `sha256`, `origin`, `status: PROCESSING/SUCCEEDED/PARTIAL/FAILED/DUPLICATE`, 件数（取込・重複スキップ・保留・エラー）, 対象期間, `duplicateOfId`。元ファイルは保存しない |
| `ImportIssue` | エラーログ | `severity: ERROR/WARNING/INFO`, シート名, 行番号, 列, コード, メッセージ（値は個人情報を含まない形でのみ記録） |
| `BankAccount` | 口座 | `bank: GMO/SENDAI`, `accountKey`（口座識別子の SHA-256）, `last4` |
| `BankTransaction` | 銀行明細 | `fingerprint`（UNIQUE：銀行・口座・日付・連番・摘要・入出金・残高のハッシュ）→ **重複取込防止**。分類: `category`, `accountTitle`, `unit`, `allocation: DIRECT/COMMON/HQ`, `behavior: LABOR/FIXED/VARIABLE`, `classifiedBy: RULE/MANUAL/TRANSFER_MATCH/NONE`, `transferPairId` |
| `ClassificationRule` | 自動分類ルール | 優先度, 対象銀行, 入出金方向, 照合フィールド（摘要/メモ）, パターン（NFKC正規化・空白除去後の部分一致）, 付与する分類 |
| `RevenueFact` | 売上の事実（月×部門） | `source: KYOTAKU_SHEET/IBOW_SALES`, `amount`, `quantity`（件数）, `detail`(JSON: 要介護/要支援/委託の件数・金額), `state: ACTIVE/SUPERSEDED/HELD` |
| `TrialBalanceLine` | 試算表の科目行 | 会計年度, `yearMonth`（決算仕訳は null）, `segment: COMPANY/HOMONKANGO/KYOTAKU`, 科目名, 金額, `state` |
| `VisitRecord` | 訪問 | `source: ZEST/IBOW`, `kind: SCHEDULED（予定）/ACTUAL（実施実績）`, 日付, 部門, `staffKey`/`subjectKey`（HMAC）, 職種, 分, 訪問種別, `cancelled`, `fingerprint` UNIQUE |
| `MetricValue` | ZEST等の指標値 | 月, 指標キー, 値 |
| `AccountTitle` | 勘定科目マスタ | `section`（売上/売上調整/原価/販管費/営業外収益/営業外費用/特別/小計）, `behavior`, `allocation` |
| `MonthClose` | 月次確定 | `yearMonth` UNIQUE, `status: OPEN/CLOSED`, 確定者, 解除理由 |
| `MonthlySnapshot` | 計算結果 | `origin` × `yearMonth` × `unit` UNIQUE, `valueStatus: ESTIMATED/RECONCILED/FINAL`, `data`(JSON) |
| `Target` / `StaffCapacity` | 目標値 / 職種別稼働可能時間（集計値のみ） | `yearMonth` × 部門 × 指標 UNIQUE |
| `AuditLog` | 監査ログ | 誰が・いつ・何を（手動分類、確定、確定解除、保留値の反映、設定変更） |

### 2.3 値の状態（推計・照合済・確定）

| 状態 | 意味 | 条件 |
|---|---|---|
| `ESTIMATED` 推計 | 業務データ（居宅売上管理表・iBow売上）や銀行明細から計算した値 | 試算表が未取込、または試算表と許容差を超えて不一致 |
| `RECONCILED` 照合済 | 業務データと試算表が許容差内で一致 | 試算表あり・月は未確定 |
| `FINAL` 確定 | 管理者が月次確定した値（試算表ベース） | `MonthClose = CLOSED`。スナップショットは凍結され、以後の再計算・取込で変わらない |

## 3. ファイル取込仕様

### 3.1 共通フロー

1. アップロード（管理者・事務）。ファイルの SHA-256 を計算。
2. **同一ファイルの再取込** → `DUPLICATE` として履歴にだけ残し、データは追加しない。
3. **種別の自動判別**（内容優先・ファイル名は補助）:

   | 種別 | 内容による判定 | ファイル名による判定 |
   |---|---|---|
   | GMO明細 | xlsx/csv の見出し行に `日付,摘要,入金金額,出金金額,残高` | `GMO` を含む |
   | 仙台銀行明細 | 見出し行に `照会口座,番号,勘定日,出金金額（円）,入金金額（円）,残高（円）` | `仙台銀行` を含む |
   | 居宅売上管理表 | xlsx のいずれかのシートに `月間売上表` と `総売上` | `居宅売上` を含む |
   | 試算表PDF | PDF テキストに `残 高 試 算 表`（空白除去後 `残高試算表`）と `損益計算書` | `試算表` を含む |
   | iBow 月次売上 | 見出し行に `利用者ID,医療総金額,介護総金額,予防総金額,…` | `SalesList*.csv` |
   | iBow 訪問実績 | 見出し行に `訪問日,ID,訪問種別,開始時間,提供時間,主訪問者` | `Implementation*.xlsx` |
   | ZEST 経営指標 | zip 内 CSV の見出しに `日別 x 職員の予定(サービスプラン・緊急) 訪問件数_対象期間` | `dashboard-経営指標*.zip` |

   内容とファイル名の判定が食い違う場合は内容を優先し、警告を記録。どちらでも判別できない場合は `FAILED`。
   ファイル名は macOS 由来の NFD 表記もあるため NFKC 正規化してから判定する。
4. 種別ごとのパーサで読み取り（下記）。行単位のエラーは `ImportIssue` に記録し、その行だけ取込まない。
5. 保存: 明細系は `fingerprint` UNIQUE で重複スキップ。月次集計系（売上・試算表）は月×部門単位で版管理:
   - 同値 → スキップ（重複）
   - 値が異なり月が未確定 → 旧版 `SUPERSEDED`、新版 `ACTIVE`
   - 値が異なり月が確定済 → 新版 `HELD`（**上書きしない**）。照合画面に「確定月の変更候補」として表示
6. 結果: エラー0件 `SUCCEEDED` / 一部取込 `PARTIAL` / 取込0件でエラーあり `FAILED`。
7. 影響月を再計算。

### 3.2 正規化ルール

| 対象 | ルール |
|---|---|
| 日付 | Excel 日付セル / `YYYYMMDD` / `YYYY/M/D` / `YYYY-M-D` / `M/D/YYYY`（仙台銀行の表示形式）/ `令和N年M月D日`。曖昧・不正な値はエラー（補完しない）。JST の暦日として保存。 |
| 年月 | `令和N年M月`（令和元年＝2019）/ `YYYY年M月` / `YYYY-MM` / `YYYY/MM` / `YYYYMM`。`令和○年○月` 等の未入力はエラー。 |
| 金額 | 数値セル、または `1,234` / `-1,234` / `△1,234` / `(1,234)` / `¥1,234` / 全角数字。小数・文字混入はエラー。**空欄は「値なし」で 0 とは区別**。 |
| 文字列 | NFKC 正規化（半角カナ→全角、全角英数→半角）、連続空白を1つに、前後空白除去。分類ルール照合時は空白をすべて除去。 |
| 事業所（部門） | `訪問看護`→`HOMONKANGO`、`居宅支援`/`居宅介護支援`→`KYOTAKU`、`事業所(合計)`→`COMPANY`。それ以外はエラー（推測しない）。 |
| 勘定科目 | 試算表の文字間空白を除去した科目名をそのまま採用（例 `給 料 手 当`→`給料手当`）。科目マスタに無い科目は警告を出して保存し、マスタ登録を促す。 |

### 3.3 種別ごとの取込

- **GMO / 仙台銀行**: 見出し行を検出し、`01-data-spec.md` の列で読む。口座識別子は SHA-256 と末尾4桁のみ保存。
  取込後に自動分類（3.5）を実行。
- **居宅売上管理表**: シートごとに処理。`月間売上表` を含むシートだけが対象。
  - 年月 = `令和N年M月` セル（未入力・解釈不可ならシートごとエラー）
  - `総売上` = ラベル右側の最初の数値
  - `要介護`・`要支援` 行 = 左ブロック（`年間売上表` の列より左）の数値6個（今月件数・金額、月後れ件数・金額、合計件数・金額）。`今月+月後れ=合計` を検算。
  - `委託` 行 = 数値2個（合計件数・金額）、`認定調査` 行 = 最後の数値（合計金額）
  - 検算 `総売上 = 要介護 + 要支援 + 委託 + 認定調査` が不一致ならシートごとエラー
  - 同一ファイル内で同じ年月のシートが複数ある場合は、どちらが正しいか判断できないため両方エラー
  - `RevenueFact(source=KYOTAKU_SHEET, unit=KYOTAKU)` として保存（状態は計算時に決定）
- **試算表 PDF**: ページごとに PDF テキストを行に再構成し、見出し（年度・部門・月列）と科目行（数値14個）を読む。
  `12か月+決算仕訳=当期合計` を行ごとに検算。全科目0の月は保存しない。`決算仕訳合計` が0以外の場合は年度の決算行として保存。
  取込後、`COMPANY = HOMONKANGO + KYOTAKU` を科目ごとに検算し差異を照合画面に表示。
- **iBow 訪問実績**: 見出し行の6列だけを読み `VisitRecord(kind=ACTUAL, source=IBOW)`。利用者ID・主訪問者はハッシュ化。
- **ZEST 経営指標**: 見出しで CSV を識別し `MetricValue(source=ZEST)`（予定ベース）。対象年月はアップロード時に指定し、日数で検算。
- **iBow 売上**: 2行目の提供月と、保険種類別の総金額・回数・自己負担額を読み、合計行と検算。利用者ID・公費番号は保存しない。

### 3.4 実ファイル確認前の扱い（廃止済み）

当初は未提供だったファイル（iBow・ZEST）向けに、列名だけを表示して管理者が列の意味を指定する「列マッピング方式」を用意したが、
全ファイルを実物で確認して専用の取込処理に置き換えたため廃止した（`ColumnMapping` テーブルも削除）。
形式が変わったファイルは見出しの検証でエラーになり、取込まれない。

### 3.5 銀行明細の分類と二重計上防止

分類カテゴリと損益への反映:

| カテゴリ | 例 | 推計損益での扱い |
|---|---|---|
| `EXPENSE` 経費 | デビット利用、口座振替、振込（家賃等） | 科目が付いていれば費用計上 |
| `PAYROLL` 給与 | 給与振込資金 | 人件費（部門不明のため共通費） |
| `TAX_SOCIAL` 税・社保 | 国税・社会保険料 | 預り金を含むため除外（要確認） |
| `INTERNAL_TRANSFER` 口座間振替 | 仙台→GMO の資金移動 | **除外** |
| `CARD_SETTLEMENT` カード引落 | クレジットカード利用代金 | **除外**（カード明細側の経費と二重になるため） |
| `LOAN_PRINCIPAL` 借入元金返済 | 返済金 | **除外** |
| `LOAN_REPAYMENT_MIXED` 元利一括返済 | 公庫返済（内訳不明） | **除外**（利息は試算表の支払利息で把握） |
| `LOAN_INTEREST` 借入利息 | 借入利息 | 営業外費用（営業利益には含めない） |
| `REVENUE_RECEIPT` 売上入金 | 国保連・ファクタリング入金 | 売上は発生主義（請求データ・試算表）で計上し、入金は照合にのみ使用 |
| `OTHER_INCOME` その他入金 | 助成金・利息・キャッシュバック | 営業外（営業利益には含めない） |
| `UNCLASSIFIED` 未分類 | ルールに該当しない | 計上しない。**未分類取引画面** に件数・金額を表示 |

- 口座間振替の自動照合: 異なる口座で「出金額＝入金額」かつ日付差 0〜3日、かつ一方が振替らしい摘要
  （`ATMフリコミ`、自社名義 `ウチケア` からの入金 等）のペアを `INTERNAL_TRANSFER` とし `transferPairId` で結ぶ。
- 手動分類は未分類取引画面で実施（監査ログに記録）。「同じ摘要を今後も自動分類する」でルール化できる。

## 4. 損益計算（Phase 2）

- 会計年度は **6月始まり**（試算表で確認）。
- 部門: `HOMONKANGO`（訪問看護）、`KYOTAKU`（居宅支援）。全社 = 2部門の合計。
- 費用区分（科目マスタで設定、画面で変更可）:
  - 直接費 `DIRECT`: 試算表の部門別金額をそのまま使う（例: 給料手当、地代家賃）
  - 共通費 `COMMON`: 全社金額を配賦基準（既定: 売上高比）で各部門に配賦（例: 通信費、ソフト利用料）
  - 本部費 `HQ`: 全社金額を本部費として別掲し、配賦基準で配賦（例: 役員報酬、支払報酬料）
  - いずれの方式でも **部門営業利益の合計＝全社営業利益**（テストで保証）
- 固定費/変動費/人件費は科目マスタの `behavior` で集計（人件費: 役員報酬・給料手当・賞与・法定福利費・通勤手当・福利厚生費）。
- 月ごとの計算元:
  1. 試算表あり → 売上・費用とも試算表。居宅は管理表の総売上、訪問看護は iBow 売上と照合し差額を表示。
  2. 試算表なし → 売上は業務データ（推計）、費用は分類済み銀行明細（推計、カード利用・未払計上・減価償却は含まない旨を表示）。
- 照合差異: ①業務データ売上 − 試算表売上（部門別）②試算表 全社 − (訪問看護+居宅支援)（科目別）③確定月の変更候補（HELD）。
  許容差は設定値（既定 0円）。

## 5. 画面構成

既存の健康経営アプリとは別のルートレイアウト（`/mos`）。PC はサイドバー、スマートフォンは上部メニュー。

| パス | 画面 | ADMIN | MANAGER | STAFF |
|---|---|:-:|:-:|:-:|
| `/mos/login` | ログイン | ○ | ○ | ○ |
| `/mos` | 経営ダッシュボード | ○ | ○ | ○（集計値のみ） |
| `/mos/pl` | 損益計算書（全社・部門別、直接/共通/本部、固定/変動/人件費、状態表示） | ○ | ○ | × |
| `/mos/imports` | ファイル取込・取込履歴 | ○ | ○ | × |
| `/mos/imports/[id]` | 取込詳細・エラーログ | ○ | ○ | × |
| `/mos/transactions` | 未分類取引の確認・手動分類 | ○ | ○ | × |
| `/mos/reconciliation` | 試算表との照合差異・確定月の変更候補 | ○ | ○ | × |
| `/mos/closing` | 月次確定・確定解除 | ○ | × | × |
| `/mos/settings` | 目標・稼働可能時間・科目マスタ・分類ルール・ユーザー | ○ | × | × |

ダッシュボードの指標（Phase 3）:

- 全社売上・営業利益・営業利益率（状態バッジ: 推計/照合済/確定）
- 事業所別売上・営業利益
- 月次目標達成率（売上・営業利益・訪問件数）
- 訪問件数（iBow 実施実績）・予定件数（ZEST）・利用者数・キャンセル件数（出典を明示）
- 職種別稼働率（実施分数 ÷ 稼働可能分数）
- 経費内訳（科目区分別）・人件費率
- データ最終更新日時（最終取込・最終再計算）
- 未分類取引（件数・金額）・未照合差額
- 個人給与・利用者情報は表示しない。職員ロールでは、部門別の人件費の **金額** を表示しない（人件費率のみ）。

## 6. 認証・アクセス制御

- メール＋パスワード（bcrypt）。セッションは署名付き JWT（`jose`、HttpOnly・SameSite=Lax・8時間）。
- `src/proxy.ts` で未ログインを `/mos/login` へリダイレクト（楽観的チェック）。各ページ・Server Action・Route Handler で
  `requireUser(roles)` により DB 上の有効ユーザーとロールを再確認（本チェック）。
- ユーザー作成: `npm run mos:create-user -- --email ... --role ADMIN`（初期管理者）、以降は設定画面。

## 7. 自動再計算

- `recalculate({ trigger })`: origin ごとに、データが存在し **未確定** の月について月×部門のスナップショットを再生成。確定月は対象外。
- 実行契機: 取込完了時（影響月のみ）、手動（設定画面）、毎朝8時（JST）。
- 実行記録は `RecalcRun`。失敗時はダッシュボードに最終成功時刻と失敗を表示。

## 8. テスト方針

- `vitest`。ドメインロジック（正規化・判別・各パーサ・分類・振替照合・損益/配賦・照合・権限マスク）は純粋関数として単体テスト。
- xlsx フィクスチャはテスト内で `exceljs` により **確認済の構造を再現した合成データ** を生成（実データは使わない）。
- DB を使う取込サービス（重複防止・確定月保護・状態遷移）は PostgreSQL のテスト用 DB で統合テスト（`DATABASE_URL_TEST`）。
