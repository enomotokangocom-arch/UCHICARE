# セキュリティ設計(Uchi care 社内ポータル)

PHPで業務システムを作るときと同じく、**「画面(ブラウザ)は信用せず、サーバー側で必ず確認する」**ことを基本にしています。
PHPではサーバーのプログラムがログインと権限を確認してからデータベースを読み書きします。このポータルでは、その確認を **データベース(Supabase / PostgreSQL)自身** が行います。そのため、画面を改ざんされても、許されていないデータは読めず、書き換えもできません。

## 1. 全体の構成

| 層 | PHPの業務システムでいうと | このポータル |
|---|---|---|
| ログイン | `password_verify` + `$_SESSION` | Supabase Auth(パスワードはハッシュ化して保存、ログイン情報は期限付きの署名済みトークン) |
| 利用者の登録 | 管理者が登録した人だけ | 管理者が登録したメールアドレス + 招待コードがないとアカウントを作れない(DBのトリガーで拒否) |
| 権限の確認 | 各ページ冒頭の `if ($user->role ...)` | DBの行レベルセキュリティ(RLS)が、読み書きのたびに役職・事業所で判定 |
| SQLインジェクション対策 | プリペアドステートメント | Supabase の API が値をすべてパラメータとして扱う(SQL文を組み立てない) |
| XSS対策 | `htmlspecialchars` | React が表示時に自動でエスケープ。印刷用HTMLは `escapeHtml` で変換 |
| CSRF対策 | トークン | ログイン情報をCookieではなく `Authorization` ヘッダーで送るため、他サイトからなりすました送信はできない |
| 外部読み込みの制限 | — | Content-Security-Policy で読み込める外部サイトを Supabase・Google などに限定 |
| 操作の記録 | アクセスログ | 監査ログ(誰が・いつ・どの記録を追加/変更/削除したか) |
| 秘密の値 | `.env`・設定ファイル | Vercel の環境変数(`ANTHROPIC_API_KEY` など)。ブラウザには送らない |

## 2. 役職と権限

役職の序列: 経営者(0) > 統括部長(1) > 管理者(2) > 責任者(3) > 主任(4) > 一般スタッフ(5)

権限の判定に使う役職・事業所は、**ログインした人の `portal_members` の行から、データベースが引き直します**。ブラウザから送られた役職は使いません。

| データ | 読める人 | 書ける人 |
|---|---|---|
| 職員・外部リンク・委員会・評価項目・職務記述書・相談窓口・報酬単価・駐車場・設定 | 全員 | 経営者・統括部長(売上取込の設定は管理者も) |
| お知らせ | 全員(事業所向けのものはその事業所) | 責任者以上(既読は本人が付ける) |
| 車両・駐車区画 | 全員 | 主任以上 |
| 議事録 | 全員 | 全員 |
| 運行記録 | 全員 | 本人・主任以上 |
| アルコールチェック | 本人・確認者・主任以上 | 本人・確認者・主任以上 |
| **個人売上・日次売上** | **本人**・自事業所の管理者・経営者/統括部長 | 自事業所の管理者・経営者/統括部長 |
| 個人の目標・目標シート | 本人・自事業所の管理者・経営者/統括部長 | 同左 |
| 部門の目標 | 全員 | その事業所の管理者・経営者/統括部長 |
| **経営数値・補助金** | その事業所の管理者・経営者/統括部長 | 同左 |
| **給与(利益ラインの計算用)** | **本人**・その事業所の管理者・経営者/統括部長 | 経営者・統括部長 |
| 事業所の固定費 | その事業所の管理者・経営者/統括部長 | 経営者・統括部長 |
| **人事評価** | 本人・評価者・自事業所の管理者・経営者/統括部長 | 同左 |
| 営業記録 | 本人・自事業所の責任者以上・経営者/統括部長 | 本人・自事業所の管理者・経営者/統括部長 |
| **難病の上限管理(患者情報)** | 同じ事業所の職員・経営者/統括部長 | 同左 |
| 監査ログ | 経営者・統括部長 | (誰も書けない。DBが自動で記録) |
| ログインアカウント | 本人(自分の行)・経営者/統括部長 | 経営者・統括部長 |

そのほかの決まり:

- 記録の「持ち主(職員)」と「事業所」は、送られてきた値ではなく**記録の中身からDBが決めます**。他人の記録を自分のものに付け替えることや、他の事業所に移すことはできません(変更前・変更後の両方に権限が必要)。
- **最後の経営者・統括部長は外せません**(全員が権限を失う事故を防ぐ)。管理者フラグは役職から自動で決まります。
- ログインと職員の結びつけ(`user_id`)は、登録時の処理以外では変更できません(アカウントの乗っ取り防止)。
- 1件の記録は200KBまで(大きなファイルを入れさせない)。

## 3. AI機能(議事録・相談窓口・健康経営)のAPI

- すべてのAPIは、最初に **ログイン中の有効な職員か** を Supabase に問い合わせて確認します(`src/lib/server/requireMember.ts`)。ログインしていない人がAIを使って利用料金を発生させることはできません。
- 健康経営のAPIは責任者以上だけが使えます。
- 送信できる大きさに上限があります。
- 相談の内容はサーバーやデータベースに保存しません。AIに送るときは患者さんの名前を伏せます。

## 4. 端末とログイン

- **操作がないまま60分たつと自動でログアウト**します。
- サーバー共有に移行したあとは、**ログアウト時にこの端末のデータを消します**(共用のパソコン・タブレットに情報を残さない)。
- 一般スタッフの端末には、サーバーが許可したデータ(自分の売上など)しか届きません。
- パスワードは8文字以上です。

## 5. 通信とヘッダー

- 通信はすべて HTTPS(Vercel が自動で設定。`Strict-Transport-Security` で強制)。
- `Content-Security-Policy`: 読み込める外部サイトを限定する
- `X-Frame-Options: DENY`: 他のサイトに埋め込ませない(クリックジャッキング対策)
- `X-Content-Type-Options: nosniff`、`Referrer-Policy`、`Permissions-Policy`(マイクは録音のため自サイトだけ許可)
- APIの応答はキャッシュしない(`Cache-Control: no-store`)

## 6. 導入の手順(管理者向け)

1. Supabase の「SQL Editor」で `supabase/setup.sql` を実行する(済んでいれば不要)
2. 続けて `supabase/security.sql` を実行する(何度実行しても問題ありません)
3. 経営者・統括部長のアカウントでポータルにログインし、「設定・マスタ」→「データ管理」→「☁ マスタだけ登録して始める」を押す
4. 以後、データはサーバーに保存され、全職員で共有されます

あわせて設定をおすすめすること:

- Vercel の「Deployment Protection」を有効にする(関係者以外はページ自体を開けない)
- Supabase の Authentication → Policies で、パスワードの最低文字数・漏えいパスワードの拒否を有効にする
- Supabase の `service_role`(secret)キーは、ポータルでは使いません。どこにも貼り付けないでください

## 7. 権限のテスト

`supabase/security.sql` は、ローカルの PostgreSQL で次の点を確認済みです。

- 一般スタッフは他の職員の売上・経営数値・他事業所向けのお知らせを読めない/書けない
- 一般スタッフは自分の役職を書き換えられない、リンクを改ざんできない
- 記録の持ち主を他人に付け替えられない、持ち主の列を偽って送っても拒否される
- 管理者は自事業所の数字だけ読み書きでき、他事業所へ移せない
- 最後の経営者・統括部長は外せない、`user_id` の乗っ取りは拒否される
- 監査ログは誰も直接書けない、管理者以外は読めない
- ログインしていない人(anon)は何も読めない
