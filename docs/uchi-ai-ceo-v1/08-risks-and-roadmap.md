# 技術的リスクと今後の拡張ポイント

## 技術的リスク

| リスク | 内容 | Phase 0での緩和策 |
|---|---|---|
| CSVスキーマの現実データとの乖離 | 実際の会計・勤怠・訪看システムのエクスポート形式は本設計の2スキーマと異なる | CSVスキーマをドキュメント化し、Phase 1でETL/マッピング層を追加できるよう `csv.ts` をパーサとドメイン変換で分離 |
| LLM出力の不安定性(JSON崩れ・数値の創作) | 説明文生成で数値を書き換えてしまうリスク | 数値はEngine側で確定済みの値をそのままUIに描画し、LLM出力は文章のみ採用。JSONパース失敗時はフォールバックテンプレートに切替 |
| localStorage容量・永続化の脆弱性 | 12ヶ月×3拠点+30名分のデータはブラウザストレージに依存し、端末をまたげない | Phase 1でPostgreSQL移行、`store.ts` のインターフェースをAPI呼び出しに差し替え可能な形に設計 |
| 予測モデルの単純化(線形トレンド) | 季節性・イベント要因を考慮しないため実データでは精度が低い可能性 | `04-forecast-engine.md` に前提を明記し、Phase 1で統計モデル(移動平均→ARIMA等)に置換可能な関数境界を用意 |
| Explainability要件とLLM生成文の整合性 | LLMの説明文がEngineの計算根拠と矛盾する可能性 | プロンプトに「与えられた数値以外を創作しない」を明記 + UIでEngine根拠を必ず併記(11章) |
| マルチテナント未実装のままの拡大 | Phase 0はシングルテナント固定値のため、複数事業者展開時に大規模改修が必要 | 型定義に `organizationId` を予約済み、DBスキーマ設計時から前提化 |
| L3以上の自動実行機能が未実装 | 承認ボタンはあるが実際の外部実行(発注・求人公開等)は行われないため、期待値とのギャップ | UI上に「Phase 0は分析・提案までのL2」であることを明示 |

## 今後の拡張ポイント(Phase 1以降)

1. 残り14意思決定(拠点別PL, KPI異常検知, 空き訪問枠, 終了利用者分析, 入院分析, 営業先別紹介率/優先順位,
   残業・業務負荷異常 等)のDecisionルール追加。`decisionType` unionと`entityType`は型として予約済み。
2. FastAPI/NestJS + PostgreSQL + Redis への切り出し(`02-data-model.md` のスキーマを採用)。
3. RBAC・tenant isolation・encryption at rest/in transit・secrets管理の実装(12章)。
4. 通知設計(P0即時〜P3週次)の実装。現状はダッシュボード表示のみで通知チャネル(メール/Slack等)は未接続。
5. Decision実行(L3以上)のワークフロー化: 承認 → `decision_actions` 生成 → 外部システム連携 → 結果学習。
6. Forecast Engineの統計的信頼区間・季節調整・異常検知(統計的外れ値検出)の高度化。
7. Audit Logの本格実装(閲覧ログ・提案ログ・承認ログ・実行結果の全記録とレポーティング)。
8. LLM Provider追加(OpenAI/Gemini)によるベンダーロックイン回避の実証。
9. モバイル最適化(CEOが外出先でも「今日判断すべきこと」を確認できるレスポンシブUI)。
