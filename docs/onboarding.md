# 入職前システム準備管理ツール(株式会社Uchi care)

新入職員のiPhone・iPad設定、Appleアカウント、各サービスのアカウント発行を、**榎本が毎回設定する状態から、管理者・事務・責任者が手順を見て完了できる状態**に移すためのツールです。

- 画面: `/onboarding`(既存アプリと同じNext.jsの中に追加)
- データ: SQLite(`data/onboarding.db`、Node.js 22 組み込みの `node:sqlite`。追加のDBサーバーは不要)
- ログイン必須。権限はすべてサーバー側で確認します。
- メール・LINE WORKS等への送信、外部サービスでのアカウント発行は行いません(依頼文の作成と記録のみ)。

## 1. 起動方法

前提: Node.js 22.13 以上

```bash
npm install

# ■ デモ(架空の職員・ダミー端末)で試す場合
ONBOARDING_DB_PATH=data/demo.db npm run onboarding:demo
ONBOARDING_DB_PATH=data/demo.db npm run dev
#   → http://localhost:3000/onboarding
#   ログインID: enomoto / admin / prep1 / prep2 / jimu / sekinin / viewer
#   共通パスワード: demo-pass-2026(デモ専用。本番では使わない)

# ■ 実データで使う場合(最初の1回だけ)
npm run onboarding:init        # 最初の管理者を作成(パスワードは画面に表示されません)
npm run build && npm start     # → http://<サーバー>:3000/onboarding
```

- 本番(`npm start`)ではログインCookieに `Secure` が付くため、HTTPSで公開してください。社内LANでHTTPのまま確認する場合のみ `ONBOARDING_INSECURE_COOKIE=1` を指定します。
- データの保存先は環境変数 `ONBOARDING_DB_PATH` で変更できます。`data/` と `backups/` はGitに含めません。

### 準備の流れ
1. 管理者が入職者を登録(準備担当者・代行担当者・確認管理者を指定)
2. 準備担当者が作業チェックリストを上から進める。作業名を押すと手順と完了条件が出ます。条件(前提作業・iPhone/iPad確認・台帳登録など)を満たさないと「完了」にできず、足りない記録が表示されます。
3. Apple: 「次の番号を予約する」(ツール上の確保)→ Apple側で人が作成 →「作成済みとして記録」(ここでメールアドレスが確定)。作成できなかった場合は理由を記録。
4. 発行依頼: サービスを選んで「依頼文を作成」→コピーして送信→「依頼した記録をつける」。メール確定前は、メールが必要な依頼は記録できません。
5. 事務・責任者が「発行済みにする」(発行日と発行ID。パスワードは入力しない)。
6. 準備担当者がサービス表でiPhone・iPadそれぞれの配置・ログイン確認・内容確認を記録。両端末でログインを確認すると「ログイン確認済み」になります(発行済みとは区別)。
7. 必須作業がすべて完了(または理由付きで対象外)になったら「準備完了にする」。
8. 管理者が端末を操作して確認し「管理者確認を記録」。
9. 貸与して「貸与を記録」(貸与日・操作説明)。

## 3. 業務ルールの実装

- **部門別の作業生成**: 訪問看護は iBOW を含む13サービス、居宅介護支援は iBOW 対象外。ZEST・eNursing は両部門。KING of 勤怠・Notion は「利用要否の確認」(管理者が入職者ごとに使用/不使用を決めるまで準備完了にできない)。居宅独自の記録・請求システムは管理設定でサービスを追加し、部門別で「必須」にします。
- **標準チェックリスト14項目**を入社日基準の期限つきで生成。配置方式が未確定のサービスがある間は「未確定サービスのアプリ・URL・配置方式を既存端末で確定する」作業(確認管理者)を追加生成します。
- **作業状態**: 未着手・進行中・発行待ち・確認待ち・完了・対象外。対象外は理由必須。任意作業は必須完了率に含めません。
- **準備完了の判定**: 必須作業(管理者確認・貸与を除く)が未完了なら準備完了にできません。準備完了後に必須作業を戻すと自動で準備中に戻ります。
- **Apple番号**: 設定「発行済みの最新番号」(初期値36)と登録済み最大番号の大きい方+1(初期は037 / uchicare037@icloud.com)。`BEGIN IMMEDIATE` トランザクションと番号・メールのUNIQUE制約で、複数人・複数プロセスが同時に予約しても重複しません。取消番号は自動では再利用せず、管理者が理由を入力して承認した場合のみ再利用。使用不可・Apple側で作成済みだった番号は再利用不可。
- **Apple Accountの割り当て**: 同一職員のiPhone・iPadに同じ会社用Apple Accountを初期値として割り当て、端末台帳で変更できます。
- **発行担当**: ZEST=責任者、iBOW・LINE WORKS=事務(メール確定後)、MCS=発行担当者未設定、eNursing=榎本(担当区分「榎本への依頼が必要」)。移管後はサービス一覧で担当区分を「移管済み」、発行担当者を変更すると、ダッシュボードの「榎本の対応が必要な作業」から外れます。
- **会社Googleアカウント**(uchicare0105@gmail.com)は基本設定に登録済み。Googleスプレッドシート・Googleマップは「会社Googleアカウントを使用」。
- **手順の版管理**: 作業は生成時点の手順を複製して持つため、標準手順を変更しても過去の完了記録は書き換わりません。進行中の入職者へは「差分を確認して適用」で行単位の差分を見て、選んだ未完了作業にだけ適用します。改訂履歴(版・日時・更新者・説明)を保存。
- **変更履歴**: 入職者・作業・担当者・手順・サービス・Apple番号・端末・ユーザー・設定の変更を、変更者・内容(変更前→変更後)・日時で記録。

### 既存のAppleアドレスの登録(運用開始時に1回)
すでに職員が使っているアドレスを台帳に「作成済み」として登録し、番号の重複を防ぎます。
1. 管理者でログインし「Apple番号」を開く
2. 社員一覧のExcelで「氏名〜事業所」の範囲(見出し行を含んでも可)をコピーし、「既存のアドレスを一括登録」に貼り付ける
3. 「内容を確認」で登録予定と除外される行を確認し、「確認した内容で登録」を押す

- 「uchicare+3桁@icloud.com」の形式のアドレスだけを番号付きで登録します(個人のGmailや uchicareplan01 などは対象外として表示)。
- 既に台帳にある番号・アドレス、一覧内の重複は登録しません。何度貼り付けても二重登録になりません。
- 登録した最大番号が「発行済みの最新番号」より大きい場合は自動で更新し、次の予約はその続きからになります。
- 職員名などの実データはGitやデモデータには含めず、ログインが必要な本番のデータベースにだけ登録してください。

## 4. 権限

| 役割 | 範囲 |
|---|---|
| 管理者 | 全体設定、入職者登録、担当変更、利用要否の決定、管理者確認、取消番号の再利用承認、変更履歴 |
| 準備担当者 | 自分が準備担当・代行担当の入職者の準備作業(端末、番号予約、依頼記録、配置・ログイン記録、準備完了、貸与記録)、期限の変更 |
| 事務・発行責任者 | 自分が発行担当(代行)のサービスがある入職者の閲覧と、そのサービスの発行状況更新、自分に割り当てられた作業 |
| 閲覧者 | 許可された事業所の入職者の進捗閲覧のみ |

権限外の閲覧・変更はAPIで 403 を返します。変更系APIはJSON以外を受け付けません(他サイトからのフォーム送信対策)。

## 5. 認証情報の扱い

- 実際のパスワード・端末パスコードを保存する列はありません。保存するのは会社の認証情報管理ツール上の**参照先**のみです。
- 参照先を閲覧できるのは管理者と、その入職者の準備担当者(代行含む)のみ。印刷・CSV・依頼文・手順書・変更履歴には含めません。
- コメント・備考・参照先などに「PW: xxxx」「パスコード=1234」のような記述があると保存を拒否します。
- Appleのパスワードを他サービスへ適用する機能はありません。依頼文には「パスワードは別途管理者から設定」と明記されます。
- 既存の管理者用認証情報資料を取り込む機能はありません。管理設定「バックアップ・認証情報」に登録方式(資料→認証情報管理ツール→このツールには参照先のみ)を示しています。
- ツールのログインパスワードはscryptでハッシュ化して保存し、セッションもトークンのハッシュのみ保存します。

## 6. バックアップと復元

```bash
npm run onboarding:backup                                   # backups/onboarding-日時.db を作成(稼働中でも可)
npm run onboarding:restore -- backups/onboarding-日時.db     # サーバー停止後に実行。復元前のDBは自動退避
```
バックアップにはユーザー情報(ハッシュ)と参照先が含まれるため、社内の安全な場所に保管してください。

## 8. 初回に管理者が入力する未設定項目

管理設定「初回に入力する未設定項目」に自動で一覧表示されます(入力すると消えます)。初期状態の主な項目:

- 基本設定: 認証情報の管理ツール名・保管庫/会社Wi-Fiの名前/端末名の命名規則/2ファクタ認証コード受信先の方針/居宅介護支援の記録・請求システム
- 全サービス: 配置方式(アプリ/Web)の確定、WebのURL・App StoreのURL、認証情報の参照先(既存端末を見て確定。推測で登録しない)
- eFAX・myBridge・ZOOM・CASIO DESIGN MAKER2・ChatGPT・会社HP・KING of 勤怠・Notion: 使用するアカウントの種類
- 発行担当者(ユーザー): ZEST(責任者)・iBOW/LINE WORKS(事務)・eNursing(榎本)の担当ユーザー、MCSの発行担当者と担当区分
- KING of 勤怠・Notion: 各部門での利用要否
- 事業所の登録、ユーザー(代表=榎本、準備担当者、事務・発行責任者、閲覧者)の登録
- 初期値(運用しながら管理設定で調整可): 標準期限(入社日の21日前〜当日)、発行希望日(入社日の7日前)、準備期限(入社日の3日前)
