# 4. System Architecture

## 4.1 レイヤードアーキテクチャ（17章準拠）

```
┌─────────────────────────────────────────────────────────────┐
│  Presentation Layer  (Next.js App Router, React)             │
│  CEO Morning / Dashboards / Chat / Scenario / Action Center  │
└───────────────────────────▲───────────────────────────────────┘
                             │ REST/API (10-api-design.md)
┌───────────────────────────┴───────────────────────────────────┐
│  Application Layer (API Routes / Server Actions)              │
│  Auth・RBAC・Tenant Context 解決・入力バリデーション           │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Data Layer                                                    │
│  Import Pipeline (CSV/Excel) → 正規化 → PostgreSQL (05章)      │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Calculation Engine（決定論、副作用なし・純粋関数）             │
│  売上/人件費率/営業利益率/稼働率/Cash Runway 等の数式計算       │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  KPI Engine                                                    │
│  Calculation Engineの出力をKPIスナップショットとして正規化・保存│
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Rule / Anomaly Engine                                         │
│  20 Decision Rules (07章) を KPI に適用、Alert生成              │
│  拠点/組織別の閾値設定を参照（ハードコード禁止）                │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Forecast Engine                                                │
│  時系列ベースの決定論的予測（線形回帰/移動平均等）+ 信頼区間     │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Decision Engine                                                 │
│  Alert + Forecast → Decision（原因分解の決定論部分、Priority、  │
│  Confidence計算）を生成。Actionの下書きを構造化データとして出力 │
└───────────────────────────▲───────────────────────────────────┘
                             │ 構造化データのみ（PII除去済み）
┌───────────────────────────┴───────────────────────────────────┐
│  LLM Reasoning Layer（Claude API）                               │
│  原因説明の自然文化・仮説生成・Action文言生成・チャット応答      │
│  出力はテキストのみ。数値の再計算はしない（8章参照）             │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Action Engine                                                   │
│  Decision → Action化、状態遷移管理（Draft〜Result Verified）     │
└───────────────────────────▲───────────────────────────────────┘
                             │
┌───────────────────────────┴───────────────────────────────────┐
│  Human Approval                                                  │
│  重要判断カテゴリは強制承認。承認/修正/保留のUIアクション         │
└─────────────────────────────────────────────────────────────────┘
```

**設計原則**: 上位（LLM Reasoning Layer）に行くほど「解釈・説明」の責務になり、下位（Calculation/KPI Engine）
ほど「事実・計算」の責務になる。LLMはCalculation EngineやKPI Engineの出力結果を**読むだけ**で、
自分で合計や比率を再計算しない（ハルシネーション防止）。

## 4.2 コンポーネント間データフロー（日次バッチ）

```
1. Data Import / 手入力により Visit, PatientEvent, FinancialRecord 等が更新される
2. 日次ジョブ（Cron）が KPI Engine を起動 → 当日時点のKPIスナップショットを作成
3. Rule/Anomaly Engine が KPIスナップショットに対して20 Decision Rulesを評価
4. 閾値超過があれば Alert を作成
5. Decision Engine が Alert + 直近KPI推移 + Forecast を使い、原因分解（決定論パート）とConfidenceを計算
   → Decision レコードを作成（status: draft）
6. LLM Reasoning Layer が Decision の構造化データ（数値・要因）を受け取り、
   - 原因説明の自然文
   - Action候補の文言・Owner候補・Deadline目安
   を生成 → Decision を ai_recommended に更新、関連する Action(draft) を作成
7. CEO Morning は当日の Decision(ai_recommended, priority上位5件) を表示
8. 経営者が承認 → Action.status = human_approved、重要判断は追加確認モーダル
9. 実行後、担当者が Action.status を更新。結果を actual_impact に記録
10. Result Verified 後、Feedback Loop（Phase4）が Expected/Actual を比較しモデル改善に利用
```

## 4.3 マルチテナンシー方式

- 全ての業務テーブルに `organization_id` を保持（05章）
- アプリケーション層で「リクエストごとのテナントコンテキスト」を解決し、DBアクセス層（Prismaミドルウェア
  もしくはPostgreSQL Row Level Security）で `organization_id` フィルタを強制する（09章参照）
- 二重防御: アプリ層のWHERE句 + DB層のRLSポリシー

## 4.4 非機能要件

| 項目 | 方針 |
|---|---|
| 可用性 | Phase1はシングルリージョンで可。SLA定義はPhase2以降 |
| パフォーマンス | CEO Morningの初期表示は事前計算済みKPIスナップショットを読むだけにし、P95 < 1.5秒を目標 |
| スケーラビリティ | 拠点数・組織数の増加に対しては水平分割不要（テナントごとのデータ量は小〜中規模） |
| 監査性 | 重要操作（承認、データ変更、ログイン）は全てAudit Logに記録（09章） |
| 障害時の挙動 | LLM Reasoning Layerが失敗してもCalculation/KPI/Rule Engineの結果は表示できる（LLMは付加価値層であり単一障害点にしない） |

## 4.5 バッチ/リアルタイムの切り分け

- KPI計算・異常検知・予測は **日次バッチ**（当日データ確定後）で十分。リアルタイム性は要求しない
- AI経営参謀チャットとScenario Simulatorのみ **オンデマンド（リクエスト時計算）**
- Data Importはアップロード時に同期的にバリデーション、KPI再計算は非同期ジョブとしてキューイング（Phase1は同期で可、データ量が小さいため）
